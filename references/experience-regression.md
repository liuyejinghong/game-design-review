# 体验回归协议

把已验证的体验损害与亮点变成可复验场景，而不是“点击没有报错”的自动通关。只在回归请求、重要体验改动后或评审收尾时加载。

## 一、两条轨道

- 固定路径回归：使用已知操作确认状态、反馈、原档接续及已修问题是否复发；允许知道答案，但不能证明新手容易发现。
- 新一轮盲玩：新上下文、合适的新废档、无解法提示，验证改变后的入口/规则能否自己被发现；只交付目标，不交付旧失败路径或达标步骤。
两轨分开出结果。固定脚本通过而盲玩仍失败时，不能关闭“可发现性”问题；文字到像素转段时必须重验输入、阅读位置和空间线索。

## 二、回归卡模板（复制到被评游戏的文档区）

```yaml
id: EXP-001
标题: 待填真实场景
类型: 问题修复 # 或亮点保护
来源发现: 待填发现编号和四尺条款
适用范围: 待填版本、阶段、目标玩家和设备
起始状态: 待填账号/存档代号与关键资源，不写秘密
目标体验: 待填玩家需要理解或完成的事
固定路径: 待填已验证的操作及检查点
盲玩目标: 待填不含控件名和答案的情境目标
可观察通过条件: 待填动作、结果与证据要求，不能写“更好玩”
失败或未测条件: 待填阻塞、时间或工具边界
必须保留: 待填原版已验证的亮点与行为
辅助边界: 待填主持何时介入；辅助完成不算无提示成功
转段标签: 观察 # 保留、重做或观察
原始证据: 待填真实文件与片段
复验记录: [] # 逐次追加版本、时间、轨道、结果、证据、限制
```

该示例不是已发生的发现。缺原始证据的假设卡必须标候选，不能当历史失败样本。

## 三、复验步骤

1. 锁定旧卡和新版本；记录存档阶段、资源、设备与可控条件。不同起点或随机事件差异须披露，不能把条件改善全归功于改动。
2. 在授权测试档执行固定路径，比较玩家可见的结果；随后由未见答案的执行者做盲玩。资源不足只能执行一轨时，另一轨明确未测。
3. 结果为 `通过 / 失败 / 未测 / 不适用`；通过须附可观察证据，不适用须有功能下线或体裁变化依据。跳过不算通过。
4. 对不稳定结果记录尝试次数、状态差异与反例；不通过删掉失败样本来制造成功率。
5. 保存版本、实际时间、帮助程度、证据文件、旧/新裁决及原因；不覆盖旧日志。若只是学会绕路，不关闭新手问题。
6. 先复验旧损害，再检查“必须保留”的亮点。修复入口但破坏高频效率，生成新发现而不是宣布全面改善。

## 四、何时重开及何时关闭

与主打体验相关的确认 P0，必须在原触发范围通过复验且反证无新阻塞后才可关闭；没有测试权限只能给关闭建议。
新手问题须有新的无提示记录；固定路径问题须有相应状态链证据；真实回访问题须原档、真实间隔，不用清档或调时钟替代。
转段 `重做` 不自动关闭，使用新的可观察达标条件重新验证；超时没测完不能改成 `不适用`。
评分若因修复上调，关联回归证据；不得承诺“改完这个必加两分”，也不抹掉其他仍在的缺陷。

## 五、归档与汇总

默认向用户展示卡与结果；授权后写入被评项目 `docs/experience-regressions/`，原始日志保留在受控证据区。该 skill 仓库只维护协议，不默认托管真实玩家资料。
汇总最少包含：版本、场景数、两轨分别通过/失败/未测数、最高影响的未解决项、保留亮点验证情况。不同范围的通过率不横向比较。
截图、录制和追踪包发布前检查账号、令牌、聊天及隐私；不提交认证状态或登录 cookies。自动校验可检查路径与字段，不能据此证明游戏已变好玩。
