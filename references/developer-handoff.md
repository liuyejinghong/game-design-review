# 开发交接与任务卡协议

任何阶段需要把已确认缺口、待决设计或关键未知交给开发方时按需加载。本协议只定义任务的提出、交接与复验接口，不把评审变成开发流程：没有实际必要的任务不建卡，也不自动执行任何实现。

## 一、何时建任务

- 只有实际必要时才建：某项验证被阻断、已确认缺口需要补齐，或存在必须先定的设计决策；没有发现不硬凑，不为每个问题生成任务卡。
- 任务分型：`实现`（补齐或修正能力）、`补测`（取证或复验）、`设计决策`（作者先选定边界，如保存范围或目标玩家）。有时下一步是补测或决策而非开发，不默认所有缺口都变功能需求。
- 未知不自动变成开发需求：先确认必要性——阻断哪项验证、为何优先于其他投入；取得用户明确的实施或操作授权后才执行，未授权的任务只建议不执行。
- 评审 skill 对游戏代码和配置保持只读；不因存在任务卡就自动调用开发 agent、安装依赖、付费或部署，也不管理工时、排期或发布流程。
- 第 9 节任务视图只是推荐与交接记录，不触发自动执行；用户授权维护本 skill 不等于授权修改被评游戏，对游戏的实施操作须另行明确授权。

## 二、来源与关闭真值

- 任务来源只引用原 run 的 C/D/B/L/G、材料证据或未测记录（`run:ID` 定位），不复制出第二份“已修复/已通过”状态。
- 开发方完成只表示交接就绪；是否关闭由复验以新证据在原台账按 [统一裁决](adjudication.md) 判定，工程输入不自动关闭条目。工程支撑 C 行可随新工程证据更新事实，玩家端缺运行证据的项仍标未测（取得运行证据后照常核验），不据此关闭玩家 D/B。
- C 行纯差距无实证损害时不带 P 级；材料中确认的规格矛盾是设计不自洽记录，不是玩家已发生的故障。
- 任务定位 ID（如 T01）不是问题 ID：不另建新问题库，原 D/B 状态仍由原协议维护。

## 三、任务卡落位与字段

唯一落位是总报告第 9 节的任务视图：可用短表格只列必要项，归档授权与总报告一致。字段按任务组合，不要求每项都写成长模板：

- 任务定位与类型（Txx；实现 / 补测 / 设计决策）
- 来源：run:refs、证据种类与版本范围
- 为什么现在：阻断哪项验证或为何优先
- 最小目标与范围、不做事项
- 依赖与待决决定
- 候选或等价方案（不是唯一许可实现）
- 工程依据（启用 SA 时）：`R09-A`/`E-SA` 引用、兼容保护与必要故障/迁移边界；方案是候选或等价方案，不写 100% 通过或零改动硬承诺（见 [系统架构与内容管线](system-architecture-pipeline.md)）
- 验收：Given / When / Then 的可观察结果及相关边界，与来源任务匹配——玩家任务用玩家可见结果，纯工程任务可用工程支撑结果，两类证据不互换（口径见 [系统架构与内容管线](system-architecture-pipeline.md)）
- 需要保护的亮点
- 开发交接：新构建、变更说明、测试入口/档、实际结果与未做项
- 独立复验要求、失败或未测的处理

scope 由主控选择；证据不足写未知，不编工时、技术栈或成本。

## 四、实施、复验与状态

- 实施与审查在不同 run、不同冻结版本上进行；旧 run 的原始发现证据不覆盖、不回写。
- 新构建实际支持目标任务后才可变更状态；开发自报完成、单元或 UI 脚本通过只是工程材料，不等于玩家端或新手行为通过。
- 复验区分独立执行验收与同一会话显式切换 verifier 的自查（后者按用户全局规则允许），记录须标明是独立验证 pass 还是自查；没有实际隔离时诚实标“自查受限”。
- 已知设计或代码答案的执行者不能关闭首访可发现性问题；自查不冒充独立验收，也不冒充独立新玩家。

## 五、可选工程核查

- 只读、已授权、与首访隔离的上下文中进行：首访封存后执行，或并行但保证不向首访执行者泄露工程答案。
- 结果用于缩小未核验范围、定位接入线索、形成补测或任务；不能以源码存在性判体验成熟。
- 游戏隐藏实现（内部场景、隐藏 DOM、存储等）不提供给盲玩执行者。
- 本节只是接入线索级的核查边界，不是 SA 的提前执行；系统性架构/管线核查（SA01–SA08）由 R09 统一承载，见 [系统架构与内容管线](system-architecture-pipeline.md)。

## 六、复验路径选择

- 固定路径回归覆盖来源卡相关路径与必要依赖，是通用要求；未覆盖的路径明确留限制，出现新的具体疑点才扩大范围；执行细节见 [体验回归](experience-regression.md)。
- 非首访类问题在固定路径实际触发并复验后可关闭，写明保护范围；不为每个存档类 bug 强制盲玩。
- 关闭首访/可发现性/引导类发现前须新的无提示记录，按 [首访协议](first-visit.md) 执行；尚未改动或未证实改动的，也不能凭固定脚本关闭；其他改动只有实际影响该能力时才追加盲玩。
- 无盲玩能力时该类发现保持未测、不关闭；固定路径通过不能证明新手可发现。
- 回访用真实时间与授权废档；不修改存储制造成功，不伪造真人情绪或留存。
- 复验结果以新版 run 证据追加来源记录与关闭/映射记录：原 D/B 按关闭规则追加状态历史，不覆盖旧日志；能力行 C 与材料审查段按新版本规格更新并引用原条目，不把旧材料声明或旧 C 已测事实回写成当时通过；材料修正是新记录加原引用，不抹掉原矛盾。

## 七、两个合成示例

两例均为合成任务卡示例，不是任何 run 的真实发现，也不代表已实测；来源用占位标注。示例引用的实际规则以本仓库协议为准，有明确出处。

### 示例 A：保存与接续（合成，非实测）

- 来源：`run:占位C行` 与对应未测记录（占位，非真实 ID）。
- 最小范围：关键资源、设施、进行中队列与目标在正常退出重进后保留；保存边界玩家可知；保存或恢复失败不假报成功、不静默覆盖可恢复数据。离线产出是否推进由玩法决定，不把“保存队列”自动扩展成“离线产出”。
- 不做：无明确需要不加账号、云同步、多槽、跨设备或运营后台。
- 验收：Given 含上述状态的有效授权测试档；When 按已支持流程正常离开、关闭并重进；Then 关键状态与离开前记录一致，或按事先说明的规则变化，玩家能定位下一步；新局不误覆盖原档。
- 边界：异常恢复只用开发方提供且获授权的隔离故障样本；缺样本时该项记未测，不擅改生产存储。
- 保护：已成立的时间/队列语义与低成本正常操作，不为保存增加每步确认。

### 示例 B：首次有效行动（合成，非实测）

- 来源：`run:占位首访候选`（占位，非真实 ID）。
- 依赖：先确认核心操作确实接入规则；按钮未接入先修接入，不靠说明文案伪装可用。
- 最小范围：可行动对象及必要线索可发现、结果可理解、能从结果建立下一步；允许场景示范、局部提示或渐进引导，保留探索与推理价值；不提前给完整答案，不默认新建长教程、配音或剧情。
- 验收：新执行者只收净化简报，在预算内独立发现并执行核心行动，并利用反馈完成相似任务（教后实际迁移）；解谜推进的作品检验公平线索与推理迁移，不强求立即说出正确答案。
- 复验：先固定路径回归，再做新盲玩；工具或隔离不足保留未测，不换成脚本自动点击。

## 八、完成条件

任务卡交回时核对：必要性有来源证据与版本；scope 可观察且有最小下一步；交接状态与原台账关闭分开记录。
缺记录或素材时如实指出，不掩盖写成“已完成”；任务完成不等于问题关闭，关闭仍按原台账与新证据判定。
