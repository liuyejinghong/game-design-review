# 统一证据与 P0/P1/P2 裁决协议

仅 R07/主评审维护最终问题台账；专项提出候选，不把几份报告拼接成多个相互矛盾的“最终清单”。沿用主 SKILL 分级，不发明评分到严重度的换算。

## 一、先分清证据、问题与决策

| 对象 | 编号例 | 使用规则 |
|---|---|---|
| 原始证据 | E-R02-003 | 一次真实观察/操作；引用不限次数，但不能计成多次复现 |
| 轮次候选 | R02-F01 | 保留最初观察、建议级别、置信度及反证；R01 由分析者在封存后填写 |
| 最终设计问题 | D001 | 每个 run 内唯一；合并来源、实际条件和最终裁决 |
| 技术故障 | B001 | 独立清单，可高优先级修复，但不自动叫 P0 设计 |
| 路线决策 | R09-A01 | 保留/转段/技术候选与验证计划，无 P 级；存 rounds/R09.md，供总报告第 8/9 节引用 |
| 亮点 / 回归卡 | L001 / G001 | 同样需要证据；保护已验证设计，不凑数量 |

跨 run 引用使用 `run_id:ID`。同版复用保留原始证据 ID 及来源；本次索引登记外部证据，不复制编号伪称新操作。

## 二、候选发现卡（可复制）

```text
候选ID：Rxx-Fxx
来源轮次／版本／存档／阶段／玩家类型：
事实：在什么条件做了什么，实际出现什么（不先写判断）
体验影响：损害了哪条理解、行动、选择或回报链
条款：四把尺子的具体编号
证据：E-ID、真实路径或会话定位、视频区间、复现步骤
建议级别：P0 / P1 / P2；未知则待裁决
置信度：确认 / 疑似 / 待确认
最强反证／替代解释／适用边界：
转段：保留 / 重做 / 观察；重做须有明确替代计划
修改建议／复验条件：
```

同一事实的观察可信度与解释可信度分别写明：点击结果已复现，不代表猜测的内部机制已确认。置信度降低不能靠严重度降档代替。

## 三、裁决流水线

1. **核验来源**：重开原始证据，核对版本、前置状态、操作、时间与工具能力。摘要、源码存在性和静态截图不能证明动态缺失。
2. **判对象**：设计规则/体验损害进入 D；技术执行故障进入 B；没触及的系统是覆盖缺口，不直接记产品违规。无法确定原因时保持候选并说明。
3. **比条件**：先看是否同一玩家阶段、功能、触发链与后果，再决定合并。黑盒只能合并证据支持的行为级问题，不猜代码根因。
4. **保留差异**：同根问题跨多个条款只计一次；不同根因造成相似感受只标关联。一个候选含独立问题应拆开并保留来源映射。
5. **处理冲突**：新手受阻而熟练者顺畅，可以同时为真；功能已存在但发现不了，也不是自动证伪。只有同条件相反结果才优先复测变量。
6. **反证补测**：每个候选 P0 尝试最强反例；优先解决可能改变主打体验/总评的争议。预算耗尽标疑似/待确认，不平均意见，也不自动取最高级。
7. **按影响分级**：确认核心规则、选择、循环或范式使主打体验失效为 P0；核心可成立但理解/反馈/操作/恢复妨碍执行为 P1；理解与行动已成立而表达/内容变化不足为 P2。
8. **排序与输出**：最终台账、覆盖、总评与复验条件互相一致；核心 P0 不被符合条款数或媒体高分抵消。不存在已证实 P0 时不为显得严厉制造一个。

路线建议不计入 P0/P1/P2。R09 的当前体验损害须引用原尺，跨 R02/R05 去重；尚未验证空间玩法、缺客户端包、不了解代码架构仅是缺口，不自动判产品失败。
引擎/画风偏好不是缺陷；未实施方案不加减当前媒体分。路线决策保留依据、备选、最小验证和撤回条件，不能只换编号把确认问题移出活跃台账。

未获充分证据的严重候选放“待确认”，注明“若成立按 P0 处理”，不计入“已确认 P0 数”。被证伪、已合并、范围外也保留可追溯记录，不作为当前活跃问题重复计数。

## 四、合并和冲突的具体例子（假设案例，不是实测）

- 新手“不知如何接着探索”、交互“关闭面板丢当前地点”、文字“返回丢阅读位置”：只有补测支持同一上下文恢复缺陷才合并；否则关联或拆分，不能仅凭“都被打断”合并。
- “找到提示后能完成”不撤销“无提示阶段始终找不到入口”；保留提示前后证据，标新手影响。若提示一直明显可见但被工具过滤，改记工具限制而非产品问题。
- “早期两个配置等效”不足以证明全局策略虚假；扩大到相关第二局面寻找优势反转。未测后期保持未知，既不虚判全局 P0，也不替后期想象深度。
- “截图未见动画”与“录制看到反馈”冲突时，优先核查触发/设置/时间窗口；撤回不成立的动态否定。真正反馈太短而难识别须另取证，不能换措辞保住原指控。
- 网络/验证码/工具访问受阻不是“游戏完全不能玩”；只有支持环境中确认的产品故障才进入 B 并影响推荐。

## 五、唯一 findings.md 的结构

文件头：run_id、skill_version、skill_commit、game_build、report_schema、覆盖范围、裁决时间及实际复核方式。
摘要分别计 `已确认设计 P0/P1/P2 / 疑似或待确认候选 / 技术故障 / 覆盖缺口`；按唯一活跃 ID 计数，不按引用数、评审员人数或条款数计数。
台账三部分：**活跃设计问题与技术故障；待确认/范围缺口；合并/证伪/关闭及变更记录**。亮点可独立保留但使用同一证据索引。

最终条目必填：
```text
最终ID：D001；来源：R01-F01、R02-F03
状态：活跃 / 待确认 / 已合并 / 已证伪 / 已关闭 / 范围外
性质／级别／置信度：设计 / P1 / 确认（技术故障用 B，不填设计级别）
标题与事实、受损体验链：
适用版本／存档条件／玩家阶段／条款：
支持与反对证据、复现步骤：
裁决理由：为什么该级别；反证如何处理；尚未覆盖什么
转段标签、依据及替代计划：
关联ID／合并去向：
修复次序：优先修复 / 优先补测 / 后续打磨；理由与依赖
修改建议、通过条件、需保护的亮点：
难度：低 / 中 / 高 / 未知（黑盒估计，不影响严重度）
```

修复次序不是严重度的别名：阻断取证的技术 bug 可先修，疑似 P0 可先补证。不要机械把“全部 P2”排在“所有低影响但简单的 P1”后面；说明核心影响、频率、恢复成本和依赖即可，不制造综合算分公式。
高分不能抵扣问题，低分也不能把所有摩擦升为 P0；只有核心承诺确实被破坏才按该级别分类。

## 六、覆盖、变更与跨版本管理

覆盖行含 `条目 / 条件与玩家阶段 / 结论 / 证据 / 未测范围`。某条件符合不覆盖其他条件的违规；一条确认违规足以保留该问题，但不能泛化到没测条件。
条目被完整检查才记符合；没有合格证据为未测；体裁本来不需要为不适用并附原因。专项没有启用不意味着其条款不适用。
每次合并、拆分、降级、撤销记录：`原ID/判定 → 新ID/判定｜新增证据｜适用条款｜理由｜时间`；仅“熟悉了”“作者说了”“修复很贵”都不是变更依据。
修复后在新 run 按回归卡复验；旧报告不重写成“当时没问题”。新卡引用旧 run:ID，只有新版本满足通过条件才关闭；只验证固定路径不能关闭首访可发现性问题。
skill 版本或评分口径改变时，旧证据重分析明确叫“新尺复评”，不是重新试玩；不要把量尺变化计成产品改善。

## 七、总报告与媒体评分出段门槛

十节总报告引用唯一最终 ID；第 6 节展示台账而非另建一套等级，第 7 节保护亮点，第 9 节链接复验条件。各视角分歧保留其适用人群，不强行抹平。
评论员可依据同版最终台账和原始证据写推荐，不按问题数扣分；评分中新事实回交 R07 更新，不只改媒体文章。
发布前逐项核对：每个确认结论可定位原始证据；每个 P0 有反证尝试及范围；重复已去重；未测没有变成通过；原型转段没有免罪；证据与文件已脱敏且路径真实。
只有协议演练或静态检查时，不能写“游戏已通过完整试玩”；没有可用证据时给缺口，不填默认分数。
