# 能力对照评审协议（通用基础）

评审按模块检查**功能/机制的有无与成熟度**，以玩家任务及同类证据判断差距。主线：识别对象与约束 → 选匹配参照 → 建能力模块表 → 实际检查有无/深度/完成度 → 对照差距与改进/替代设计 → 四尺只判真实体验损害。本协议由总控在 Phase 0、Phase 2/3、R02–R05 与 R07/报告第 5 节按需接入；不新增 skill、轮次、尺子或报告章节。首次评审、没有可靠基线或材料/设计评审请求时，总控先读 [开发准备度](development-readiness.md) 的材料审查与最小可玩核验，再进本主线。四把尺子与阶段校准见 [主 SKILL](../SKILL.md)，轮次交接见 [轮次编排](orchestration.md)，候选到最终裁决见 [统一裁决](adjudication.md)。

**隔离要求**：本协议是通用总控的必读件。R01 盲玩执行者只读盲玩角色卡与净化简报，不得接收基准答案、参照结论、正确路线或本文件内容。

## 一、评审主线（顺序步骤）

1. **识别对象与约束**：类型/子类、平台与输入方式、目标玩家、当前阶段、单次会话成本（时长、回访间隔）、主打体验；写入 Phase 0 定靶，依据不足标暂定。
2. **选匹配参照**：从 [参照游戏库](benchmarks.md) 选 2–4 个与目标玩家任务相同的成熟样本，建本 run 初始画像；某模块需要时再补最好实践或不同设计样本。
3. **建能力模块表**：以第三节默认候选为起点，按识别结果增删替换（FPS、经营等换入类型模块），并标适用性与关注理由。
4. **实际检查**：对适用模块查有无、深度、完成度；走一条完整玩家任务加正常中断/边界场景。
5. **对照与替代**：按第六节结论维度写差距；非传统实现按第七节公平核查。
6. **判损害**：四尺裁决对照中已实证的体验损害；缺功能/模块行照常完整记录，不等于缺能力即判 P，差距与建议留在对照表。
7. **按范围收口**：完整/里程碑评审对核心与匹配模块逐模块对照；局部/迭代只涉及相关模块及依赖，复用已有研究，不重做全量参照调研。

## 二、基准条目写法（每条参照）

先写**玩家任务/要达到的能力**，再列典型实现；下列均为合成例，不编竞品事实：

- 会话接续：玩家任务“今天退出、明天接着经营”→ 典型实现（合成例）：手动多槽存档、自动保存与恢复、持久世界。
- 观察与导航：玩家任务“看清并控制空间关系”→ 典型实现（合成例）：缩放/旋转、固定概览、镜头边界。
- 规划与执行：玩家任务“先规划再施工，避免昂贵试错”→ 典型实现（合成例）：蓝图/预览规划、撤销或分期施工。
- 交战反馈（供类型改写）：玩家任务“判断是否命中与命中质量”→ 典型实现（合成例）：瞄准反馈、命中确认、后坐或冷却表达。

每条另标：**版本/平台/日期｜来源类型（官方手册、实测、视频、社区）｜确切声明｜已核验或待核查**。

- 官方手册能证明“提供了某功能”，不能证明实际手感、速度或效果；动态对比需实玩或等价原始证据。
- 参照说明不是目标实测：不把“它通常如此”写成目标问题，也不用参照结论代替本轮操作证据。
- 少样本只写“在已查样本中出现”，禁止“几乎所有”“行业强制”或统计普遍性。
- 参照表现形态可不同，但玩家任务须匹配，并写明不能比较的范围（平台/阶段/会话成本）；无需每条凑 2–4 样本，没有已验证来源标待核查。
- 能力行不必等凑足参照才登记：先按玩家任务与材料查必要性与材料状态，字段见 [开发准备度](development-readiness.md) 的材料审查记录；参照来源不全时，参照栏标待核查，对照结论记未能判定；材料结论独立成立，不互相顶替。
- 资料复用不足时可由主控按需触发 primary 调研并更新参照记录；本协议不是自动研究工具，更新以可信来源为准、未核验明确标注。

## 三、默认候选模块（可替换组）

不是全游戏硬清单；按识别结果替换、合并或删减，替换项写理由。

| 模块 | 玩家任务（要达到的能力） | 默认关注理由 |
|---|---|---|
| 会话接续/成果保存 | 中断后回到原行动与成果，不被无提示丢失 | 核心支撑（长会话/跨会话） |
| 观察与导航/镜头 | 看清世界关系与自身位置，找到目标 | 核心支撑（空间型）或条件增强 |
| 核心输入交互 | 用已支持输入完成行动，映射可发现可预期 | 核心支撑 |
| 状态/因果/行动反馈 | 每个行动能知道受理、结果与原因 | 核心支撑 |
| 核心规则/系统关系与有效选择 | 规则可推演，选择有真实后果 | 核心支撑 |
| 学习/帮助 | 需要时就地学会规则与操作 | 匹配参照常见做法 |
| 目标/成长/长期循环 | 有当下目标与跨会话积累理由 | 核心支撑（长期型） |
| 平台适配/防错/恢复 | 目标设备上可控；低损操作有保护与恢复 | 匹配参照常见做法或条件增强 |

类型替换：FPS 换入移动瞄准、武器循环、交战反馈、关卡或赛局；模拟经营换入资源、物流、规划、服务。模拟经营只是类型样本，FPS 同样可替换。玩家需求不只来自项目宣传/承诺：基准里的同类任务与投入水平能识别**未宣称但必要**的能力（如无预告的丢失成本），照常登记检查。

## 四、适用性判定

- 每个模块先从类型任务、平台/输入、阶段、主打体验论证适用或增强，而不是看“有没有这个按钮”。
- 关注理由默认取模块表标注；调整为其他类别须在行内写理由。
- 缺失、不完善、不符合传统实现的，都放适用能力行呈现；只有能力本身对当前类型任务不需要且有依据，才标不适用。
- 传统实现缺失与能力不适用是两层：目标没提供某传统做法时，该能力行不能消失，须写“传统实现未提供，能力由 X 替代／当前不需，因为…”，并给出依据。
- 阶段预算只影响建议时机与深度预期，不能把当前真实损害改成通过。
- 反例约束：短单局不强制持久保存；2D 不要求俯仰；不是所有 FPS 都需要 reload/ADS；不是所有经营都需要离线收益。

## 五、实现状态（独立于覆盖与 P 级）

四态：**具备 / 部分具备 / 已确认缺失 / 未核验**。记录正常路径、菜单与游戏内帮助的查找路径及实际可执行动作。

- 没找到不自动证明“完全没有”：限定已查范围，写未核验与补测动作。
- 当前无法执行、阶段不可达或工具不足 = 未核验；相关四尺覆盖随之为未测，不替缺失做判断。
- 公开文档、开发声明只能标来源，不能代替实玩结论；其存在或缺失都不等于实玩核验（此为玩家任务行口径；工程支撑行的静态事实口径见 [系统架构与内容管线](system-architecture-pipeline.md)）。
- 材料状态与材料结论是独立维度，记录落点见 [开发准备度](development-readiness.md) 的 run 材料审查段，与本节四态分开：材料未交代不写成未核验，更不写成已确认缺失。
- 确认缺失需与所述范围相称的证据：菜单/帮助/正常路径查找加必要复核；多点缺入口只证明不可发现，不能证全局缺失，确认缺失须写明范围。
- 发现不了入口造成的实际损害可按四尺查，即使底层功能也许存在；结论按已查到的入口与信息写，不泛化成“隐藏等于没有”。

## 六、对照结论（独立维度）

五值：**达到参照 / 部分达到 / 存在差距 / 替代成立 / 未能判定**，均限定任务、规模、设备与已测范围；不是数值打分，也不是机械满足功能数量。

- 按钮不等于深度：走完一条完整任务加一次正常中断/边界场景，看发现成本、代价与结果、恢复、规模变化后的表现、重复工作负担。
- 相同键位、命名或视觉不是硬标准；用不同呈现实现同一能力时，按第七节查映射、发现与结果。
- 未能判定用于证据不足或范围不可比，不与“存在差距”混用。
- 启用 SA 工程核查时（触发、时序与承载见 [系统架构与内容管线](system-architecture-pipeline.md)），矩阵另加工程支撑行：模块/任务首字段显式 `工程支撑：…`，实现状态沿第五节四态、对照结论沿本节五值，沿用既有矩阵列，不新增字段或状态；证据用 `E-SA-xxx`，参照匹配与静态判法以该附件为唯一事实源；工程行写明证据支持范围与未验证运行边界，纯工程差距不设 D/P/B。

## 七、替代设计的公平处理

非传统实现、自研方案或有意省略同一能力时，依次做：

1. 登记它试图解决的玩家任务；
2. 在同约束下核查完成度、代价与恢复（怎么用、用错怎么办）；
3. 在至少一个相关不同局面验证，不只看单一路径；
4. 主动找最强不利例，记录收益与限制。

有正证据才写“替代成立”；已有负证据或部分任务未完成时，按第六节记部分达到／存在差距，只有证据不足才记未能判定——不因“没有替代成功正证据”把已确认差距统一归为未知。观察不足者留作待验假设，作者有意创新不等于成立。传统实现缺失与替代能力成立可同时写在同一行。合理省略能力必须说明该类型/模式为何不需要，不能因为“没提供”自动豁免。被证实的亮点与回归条件照常保留。

## 八、能力差距与设计缺陷的关系

- 可见差距（含与参照的明确差距）但无真实损害记录：照常完整记录模块与差距，只进对照表与建议，不强行 D/P 级。
- 四尺确认损害才成候选：核心规则/选择/循环被破坏且有反证 → 候选 P0（进 D）；执行摩擦 → P1；表达不足 → P2；技术故障走 B，不自动改叫 P0。
- 功能多、对照行多数达标不保证好玩；一条非核心差距不自动等于不好玩。
- 差距与严重度、修复优先独立；媒体评分依既有证据与协议，不加新分数公式。

## 九、输出：报告第 5 节的“能力对照表”

行格式（run 内编号如 C01 只作**对照定位**，不是 D 问题 ID）：

| 对照行 | 模块/玩家任务 | 适用与关注理由 | 成熟参照行为/版本来源 | 目标实现状态及实际做法/证据 | 对照结论/差距与替代 | 建议/复验 | 关联原尺/问题或亮点 |
|---|---|---|---|---|---|---|---|
| C01 | … | … | … | … | … | … | … |

- 对照表挂在总报告第 5 节，与原四尺覆盖并列；不新建报告章节，不建第二问题台账；候选引用已有 `Rxx-F`，最终引用 `D/B/L/G`。
- 完整报告须明确写出“距成熟同类差在哪”及按影响排序的优先建议；即使未发现设计问题，也照常交付能力对照矩阵（可为全部达到参照）。
- 完整评审对核心与匹配模块逐行输出；局部评审声明涉及模块与依赖，不做全覆盖，也不声称全局成熟度。
- 证据可复用同版 ID，但不能计成多次复现；关键子任务与边界场景证据可在相关模块间复用。
- 不为每个模块另建模板文件，也不设固定动作配额；模块粒度由实际任务决定，不细化到每个按钮。

## 十一、完成条件与缺口

范围内每个核心模块至少满足：有基准来源或明确待核查；有目标证据或未核验原因与补测动作；有差距/替代结论、建议与复验方式；确认结论不超过任务/规模/设备/已测范围。

- 存在资料或工具缺口时仍交**部分矩阵**，不因缺口放弃其余模块。
- 没有入口/授权时不做动态对照，也不冒充全球成熟度或评分。
- 类型专项（3D、经营）读 [3D 空间与操控](3d-gameplay.md)、[模拟经营](management-simulation.md) 的方法部分，本协议不复制其条款；确认问题或复验请求按需读 [体验回归](experience-regression.md)。
- 资料复用不足时按需补查可信来源并更新参照，未核验明确标注；本协议不自动执行游戏、不自动安装工具。
