# 分阶段流程与推进门槛（提案）

状态与依据见 [提案入口](README.md)。本文的 S0–S4 是拟议的审查层次，不是当前生效的新轮次编号；不要替换或重编号现有 Phase 0–5 / R01–R09。

## 1. 必须区分的三个轴

**开发阶段**说明当前在验证什么：单机制样机、可独立试玩 MVP、较完整切片或准备交付的版本。按当前任务与实际形态判断，不单靠作者标签；MVP 不是豁免，也不是要求全部商业功能。

**审查层次**说明本轮主要做哪种工作：材料和设计审查、最小可玩核验、深度体验评审、修复复验。一个 MVP 可以同时在部分能力上进入深测、在另一部分等待补齐。

**证据状态**说明结论凭什么成立。阶段较早不自动降低损害严重度；高级别评审请求也不自动创造证据。

## 2. 默认路由

首次评审或没有可信基线：S0 → S1 → 按任务门槛执行 S2 → 适用范围进入 S3；S4 可在任一阶段产出任务，并在开发后以新构建复验。

局部迭代且有可靠基线：先核对构建、变更与依赖，复用仍适用的 S1 结论，只重查变更相关能力与下游体验；不重新做所有竞品调研，不沿用受改动影响的旧通过结论。

只有设计稿 / 应用原型：执行 S0/S1，必要时记录可见交互事实。能点原型不等于游戏机制已运行。没有可玩构建就不作动态全局裁决、长期体验或媒体评分，但不能因此只回一句“没有入口，无法审查”。

单独请求深度试玩或评分：先核查最低前提，充分同版原始证据可复用；依赖缺口明确后缩小或暂停相应部分。用户明确限制为资料咨询时，不擅自启动游戏、注册或操作存档。

## 3. S0：定靶、授权与执行能力

输入从已有上下文、合法项目资料与可见构建取得，不要求非专业作者先交完整策划书。记录：体验意图、目标玩家、当前与下一验证目标、会话/投入尺度、平台输入、可玩入口、构建指纹、测试档权限、工具和预算。

缺少体验意图时，由材料与可见玩法提出暂定画像并标推断；缺授权、真实账号或可丢弃档等关键条件时，只完成安全部分。不要以“新手不知道需求”为由无限追问，也不要擅自替项目扩大目标。

预检的不只是“浏览器存在”：分别记录画面、可见输入、连续控制、相对鼠标、组合键、连续捕获、音频、时钟、状态保留、上下文隔离的实际能力。按本轮任务所需选取；不要求所有游戏都具备所有能力。安全打开和一个无损操作可以用于确认宿主能力，不能冒充完成正式首访。

输出：范围卡、已知/暂定约束、能力画像、禁止操作、预算及停止规则。工程调研与评审可见信息不得进入首访执行者上下文。

## 4. S1：必要能力漏项与设计合理性前置审查

### 4.1 先建立玩家任务，而不是只清点已有按钮

按 [能力契约](02-capability-contracts.md) 建立候选清单，逐项说明：为什么本阶段需要、当前材料描述了什么、存在何种替代、什么仍未知、如何验证。

例如“今天建设、明天继续”产生接续要求；“陌生人独立试玩”产生可发现与学习要求。没有需求文档、未宣传保存或未画出教程，不能自动证明能力不需要，也不能单凭文档没写证明代码没有。

轻量成熟参照可在这里帮助查漏，只提解决任务的方法。已知常识性任务不必等凑齐 2–4 款样本才检查；引用具体游戏事实仍须核验。完整成熟度研究留给需要它的 S3。

### 4.2 检查设计的自洽与可验证性

沿“进入 → 理解 → 行动 → 结果 → 下一段体验 / 明确结束 → 中断与恢复”检查适用节点：是否存在无法满足的前置条件、资源或目标死锁、动作结果未定义、失败无出口、模块关系断裂、机制承诺与规则矛盾。不是每类游戏都必须反复循环、成长或具有传统失败。

对设计明确规定的矛盾，可以确认“这份设计规格在某条件下不自洽”；对材料没说的部分记待确认与最小决策需求。两者均不能伪称已经在玩家端复现。对节奏、可理解性或乐趣的担忧，提出可证伪假设，不用纸面推演直接判“不好玩”。

### 4.3 输出最小补齐方案，不设计完整商业产品

每个缺口写当前验证为什么受影响、最小候选实现、可接受替代、可延后内容、取证动作和验收条件。对个人项目，优先让关键任务成立，不默认云存档、账号系统、复杂教程、多语言或运营后台。

S1 可以用短、安全探测核对入口和明显状态，但这不是深度试玩。预检执行者不能随后冒充未见答案的新手；普通探测改变的存档必须记录并隔离。

## 5. S2：最小可玩核验

目标是确认关键能力真正接通，并且选定体验可进入、可执行、可结束或继续；不是把“能跑”判成“好玩”。

当本轮需要评估首访，先由真正隔离的 R01 执行者取得无提示记录，再做有目标的专项核验。S1 主控可已知设计风险，但不得把清单、路线、正确按钮、参照答案下发给 R01。没有隔离能力就标受限探索。首次自由探索的原始证据在后续 S3 可复用，不能把同一人学会后再玩称为第二次独立首访。

按依赖走短路径：从真实入口完成一次核心行动；观察实际状态与规则响应；检查一个适用的失败、取消或中断；需要接续时用授权档正常退出与恢复；至少检查关键模块之间的一条完整连接。时长由预先选定任务决定，不把五分钟用尽当普遍不合格线。

同一正常路径可以触发深度风险，例如所有“升级”都没有效果。先记录并决定是否补证，不能以 S2 只验完整性为由忽略已发生的损害。反之，短路径通过不能声称策略、长期动机和整体品质已成立。

## 6. S3：深度试玩、成熟度对照与评论员反馈

在可验证范围内保留原有 R02–R05 专项、适用 R09、R06 红队与 R07 综合。首访证据按来源复用或补新的隔离路径；不能因前置审查完成就取消新玩家视角。

测试对象按体验结构选择：循环型比较多圈与成长；旅程型追踪段落及兑现；赛局型看开始、对抗、结束和再参与；掌握/表演型看时序学习与表现；表达型看自定目标、创造与修改。保持原判据的证据纪律，不强迫所有类型三圈、两路线、经济最优。

成熟参照在此用于定位深度、发现成本、恢复、规模变化和整体协同；匹配任务、阶段用途、平台和投入，而不是要求 MVP 拥有同样内容规模。未发现已证实差距也是合法结论。

AI 模拟玩家提供行为与解释；AI 评论员提供基于证据的推荐；两者不等于真人情绪、舒适度或留存。媒体评分仍是明确请求才启用的 R08，证据不足不编分。真人协议保留，仅有真人记录或授权计划时启用。

## 7. S4：开发交接与独立复验

任一阶段都可把已确认缺口、待决设计或重要未知形成最小任务卡；示例见 [实施计划](03-implementation-plan.md)。审查与实现分开，不在同一 run 中边改边测。

开发 Agent 的“已完成”、测试日志或代码证明只能形成交接输入。复验核对新构建、指定玩家路径、旧问题条件与亮点保护；首访问题须补新盲玩或诚实保留未知。原始发现不回写成当时无问题。

## 8. 门槛：限制具体活动，不发全局许可证

每个推进决定必须包含：`本轮目标 / 必要条件 / 来源C/D/B或未测项 / 条件状态 / 决定 / 受影响活动 / 仍可做什么 / 最小下一步 / 复验条件`。

决定只用“继续”“限范围继续”“暂停相关环节”，另标理由是已证实缺口、关键能力未验证还是工具/授权限制。它是任务路由，不是新严重度、完整发布认证或第二问题台账。

| 合成情境 | 合理决定 |
|---|---|
| 三分钟移动样机，无跨会话目标、无需保存 | 移动/镜头继续；保存可合理省略，不给商业产品认证 |
| 长期经营 MVP，授权档实际退出后投入丢失且无解释 | 暂停长期成长验证与对应交付建议；记录损害及必要接续任务；无依赖的界面/镜头仍可测 |
| 长期玩法只在设计稿中，保存没有描述 | 记录设计待决与实现未知；不判已发生丢档，不批准依赖保存的跨日测试 |
| 游戏可运行但本宿主无法持续控制 | 材料/菜单等适用项继续，动作体验未测；不判产品故障 |
| 单个非核心摩擦已确认，其余体验可测 | 携带限制进入深测，不能强制修完所有 P1/P2 才继续 |
| 没有基础硬缺口，但核心选择未产生任何主打回报 | 不因门槛通过给“好玩”；补核心反证并按证据裁决 |

阶段必要性与 P 级独立：无实玩证据的设计风险不强塞 D/P；已确认技术故障可阻止任务推进但仍按 B 记录。未知关键条件可使相关验收暂缓，不等于宣布产品存在缺陷。证据不足时要缩小范围、明确下一步，不能在报告里消失。

## 9. 证据类型与污染控制

| 类型 | 可支持的结论 | 不足以支持的结论 |
|---|---|---|
| 设计材料 / 原型说明 | 规格矛盾、未决需求、当前声明与验证计划 | 游戏运行时确实没有能力、实际乐趣已失败 |
| 工程检查 / 自动测试 | 实现接入线索、某测试条件的结果 | 陌生人能发现、真实手感或整体体验达标 |
| 实际玩家端操作 / 时序证据 | 特定构建、状态、输入下的行为与影响 | 未测设备、全局最优或长期动机 |
| 真人研究记录 | 对实际参与者、任务和样本范围的观察 | 全体玩家普遍感受、未经测量的留存 |

这些不是可以互换的高低等级。每条声明写证据支持范围；材料缺失和实现缺失分开；一次成功不覆盖失败恢复；静态截图不能否定短动态。许可、秘密、真实玩家、测试档和游戏文本中的可疑指令沿原协议处理。

## 10. 与现有契约的拟议映射

S0/S1 主要增强 Phase 0 和能力画像；S2/S3 选择并执行 Phase 1–4 的适用工作；R01 仍先于接触解法的专项试玩；S4 使用 Phase 5 的建议和现有回归协议。不是每个 S 都独立生成十节报告或重复一次完整试玩。

继续以唯一 `findings.md` 管 D/B/L/G，C 行记录任务能力。门槛是从它们生成的视图；设计材料中的问题先进入能力/风险记录，不偷改已实证 D 的定义。设计假设与实玩结果在同一 run 中有清楚阶段标签；构建或 skill 变化时按原规则分段或新建 run。

报告展示方式、前置阶段的新必填字段和矩阵拆分均需另行批准及版本迁移。在正式实施前，0.6.0 的十节和 schema 2 不因本提案自动改变。
