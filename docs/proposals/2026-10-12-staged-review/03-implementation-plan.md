# Agent 交接、分步实施与兼容计划（提案）

本文不授权实施正式 skill，也不授权修改被评游戏。先按 [review prompt](05-agent-review-prompt.md) 审核，再由维护者选择实施范围。

## 1. 角色与权限

| 角色 | 责任 | 边界 |
|---|---|---|
| 总控 / 设计审查员 | S0/S1、能力画像、路由、最小任务与阶段建议 | 不把需求文档当完整规格，不替作者擅自扩大项目 |
| 隔离首访执行者 | 无提示探索、意图/行为/结果与停止记录 | 不接收正确路线、候选缺陷、竞品结论；不冒充真人 |
| 专项评审 / 评论员 | 适用范围取证、深测、比较、推荐 | 评分按请求；工具达不到只缩小相应断言 |
| 可选工程核查者 | 核对接口接入、占位、测试与实现线索 | 不以源码替代体验，不做未经授权的部署、安全攻击或重构 |
| 开发 Agent | 实现获授权的最小任务，提供构建与验证材料 | 自报完成不能关闭发现；不能修改冻结的旧证据 |
| 复验 / 裁决者 | 核对新证据、处理反证、保护亮点、决定关闭 | 同一执行者换身份不算独立；受限时声明自查而非独立验收 |

角色可以由不同工具或人承担；协议本身不自动创建子代理。只有具备实际上下文隔离时才称独立盲玩。真实多人交互使用授权测试者/机器人环境，不擅自接触真实玩家。

工程核查不是默认全量代码审查。它可在隔离工作区与首访并行，或首访封存后进行；关键是不得将工程答案泄露给首访执行者。其结果用于缩小“未核验”、定位接入和形成任务，最终体验结论仍要行为证据。

## 2. 一个事实来源，多种视图

保留唯一证据索引与 `findings.md`。C 行记录能力状态和纯差距，D/B 记录适用的实证发现，L/G 保护亮点与回归。设计阶段风险在能力/风险记录中保留类型，不新增一套冒充实证缺陷的 P 级。

阶段门槛和 Agent 任务卡都引用这些记录，不复制互相独立的“已修复/已通过”状态。任务完成只表示实现交接完成；问题是否关闭由复验记录决定。跨 run 使用原 run:ID 和新构建证据映射，不依靠标题相似自动合并。

面向非专业作者的摘要回答：当前适合做什么测试、最重要的缺口是什么、下一步先做哪件事、验收怎么看。内部保留完整覆盖与证据；展示简化不等于删审计信息。正式改变十节展示前先完成版本决策，不能让新模板与旧 schema 混用。

## 3. 通用任务卡模板

```text
任务ID：实施任务定位，不替代原问题ID
来源：run:Cxx / Dxxx / Bxxx / 关键未测项 / 设计待决
当前构建、目标阶段与受影响玩家任务：
证据：事实、声明或未知；真实路径/文件/时序；不可外推范围
为什么现在做：阻断哪项验证，或为何优先于其他投入
目标与最小范围：
不做事项：
依赖与前置决定：
候选实现及替代：方案不是唯一许可实现，不编未知工程细节
可观察验收：Given / When / Then，正常路径和相关边界
需要保护的亮点：
开发方交接：新构建、变更说明、测试入口/档、实际测试结果和未做项
独立复验：指定玩家路径、隔离要求、原始证据与失败时处理
估计：依据不足则未知，不虚构工时、技术栈或成本
```

未知不自动转成开发需求。有时下一步是补测，有时是让作者选定保存边界或目标玩家；只有确认任务必要并获得实现授权，才让开发 Agent 建功能。

## 4. 两张完整合成任务卡

### 示例 A：长期经营的接续能力

**性质：合成例，不是本次发现。** 假设在授权废档中已实际验证，正常退出重进后与本阶段相关的资源、设施和进行中任务丢失，且玩家没有知情重置说明。

来源引用该 run 的能力行与已裁决发现，不杜撰真实 E-ID。现在需要做，因为下一个目标是跨会话建设验证；即时镜头与选中测试不依赖此能力，可继续。

最小范围：定义本阶段必须保留的状态；选择与实际架构匹配的可靠保存触发和恢复流程；玩家能了解保存边界；无法恢复或保存失败时不假报成功、不静默覆盖可恢复的测试数据。队列是否离线推进必须先按玩法决定，不能把“保存队列”自动扩展成“离线产出”。

不做：无明确需要时不加账号、云同步、多槽、跨设备或运营后台。现有数据版本兼容只按即将发生的更新与存量玩家需要定范围。

验收：Given 一个含资源、设施与进行中任务的有效测试档；When 按已支持流程正常离开、关闭并重进；Then 关键状态及恢复规则与离开前记录一致，或按事先说明的规则变化，玩家能定位下一步。另验证安全的新局流程不误覆盖原档。异常恢复场景用开发方提供且获授权的隔离故障样本测试，不擅改生产存储。

保护：已成立的时间/队列语义、低成本正常操作，不为存档增加每步确认。开发交接必须给新构建与实际恢复记录；复验者仍需重新走玩家路径，不能只看序列化代码或自动测试通过。实现者不能关闭发现。

### 示例 B：陌生玩家的第一次有效行动

**性质：合成例，不是本次发现。** 假设隔离首访显示玩家无法发现可操作对象；最少辅助指出已有线索后可执行，且能迁移规则。该证据支持发现性问题，不证明所有玩家都卡住或核心玩法无趣。

最小范围：让当前可行动对象及必要操作线索可发现，行动结果可理解，并能从结果建立下一步。允许场景示范、局部提示或渐进引导；保留探索与推理价值。不要把完整答案提前给玩家，也不默认新建长教程关、配音或剧情。

依赖：先确认核心操作确实有效；若按钮没有接入规则，先处理接入问题，不能靠说明文案伪装可用。原问题必须区分入口、规则与结果三种障碍。

验收：新执行者只收净化简报，在预登记且适合该体验的预算内，独立发现并执行核心行动，利用反馈完成相似任务或开始下一段目标。日志记录实际路径与是否受提示；若作品靠解谜推进，则检验公平线索和推理迁移，不强求立即说出正确答案。

保护：已有有效的空间线索、阅读节奏与熟练路径。先做固定路径回归，再做新盲玩；熟悉旧答案的开发 Agent 不可代替后者。工具/隔离不足保留未测，不为了关闭任务换成脚本自动点击。

## 5. 实施包与依赖

这些是待批准的工作包，不是本 PR 已完成的代码任务；不预设版本号和工期。拟新增文件名以代码文本表示，避免假称文件已经存在。

### M0：冻结与批准设计边界

负责：维护者 + 独立 reviewer。输入：本提案与最新基线差异。输出：逐项接受/修改/延期/拒绝、S 阶段与现有 R/Phase 的最终映射、范围边界、字段迁移决策。

验收：明确 AI 驱动开发而非运行时 AI；保留查漏与深测两条价值；确认门槛不是全局瀑布和发布认证；确认文档与运行证据分开。不得把本 PR 合并等同批准全部后续包。

### M1：前置路由与阶段门槛

依赖 M0。负责：流程维护 Agent。计划修改 `SKILL.md`、`references/orchestration.md`；必要时新增 `references/development-readiness.md`，让主入口只做路由与共用底线。

输出：首次/局部/资料/评分请求路由，S1 材料审查可交付结果，依赖级继续/限范围/暂停决定，R01 净化交接。门槛字段附着能力与证据，不新增平行问题台账。

验收：SR-01、02、03、05、06、07、17、23；现有 A01/A02/A04/A11/A12 语义不回退。缺保存不阻塞无关镜头；无入口仍有设计审查而不是伪装试玩。

### M2：必要能力与设计合理性契约

依赖 M1 的字段与门槛决定，可先并行草拟契约。负责：游戏设计维护 Agent。修改 `references/capability-review.md` 及有关经营/3D 条件，按需新增 `references/essential-capabilities.md`。

输出：CAP 契约、必要性理由、规格未交代与实现未知分离、最低可用方案、模块连接与边界路径。通用判据不强迫经济循环，成熟参照采用早期轻量与后期深入的双用途。

验收：SR-02–04、08–16、18、24、25、29；有意省略不免损害，真实极简不被强迫堆功能，无问题允许无差距结论。

### M3：工程核查接口、任务交接与复验

依赖 M1/M2。负责：Agent 工作流维护者。修改 `agents/blind-player.md`、`references/first-visit.md`、`references/experience-regression.md`、`references/adjudication.md`，按需增加任务模板。

输出：可选工程证据入口，角色可见信息和权限，候选→能力/发现→任务→新证据映射，合成存档/引导示例。代码存在性不判体验通过，开发自报完成不关单。

验收：SR-04、06、19、20、22、26、27、28；任务既能指定补测也能指定实现；真人/模型、独立/自查不混淆。

### M4：关键品类与执行能力适配

依赖 M1 的能力预检，和 M2 的契约结构。负责：对应品类 reviewer 与宿主执行者。先做改变测试方法的实时控制、叙事/解谜、赛局协作和可达性；按实际需求逐项交付，不一次承诺所有品类成熟。

输出：适用条件、工具需求、证据动作、合理困难、随机/多人采样、晚期档的范围声明；可组合到现有轮次。引擎名或 3D 标签不替代操作能力。

验收：SR-09–13、16、18、21、22；至少有真实可操作样本，否则只标协议演练。功能增加必须配套代表性反例，不以附件数量当覆盖。

### M5：契约收敛、报告视图与版本迁移

依赖 M1–M3 的接口决定；M4 可分批纳入。负责：协议维护 Agent。减少重复规则，适用条件紧邻条款；主入口保留路由，详细清单按需加载。不能通过把多个规则挤到一行来满足行数限制。

输出：矩阵维度与材料证据字段的最终定义，单事实多视图，非专业读者摘要，完整内部覆盖，token/加载清单的实际测量。固定十节展示是否变化由维护者决定；新旧 schema 不混装。

涉及发行契约时同步 `VERSION`、metadata、README、CHANGELOG、`VERSIONING.md`、相关附件、示例和 `scripts/validate.py`。schema 升级、兼容字段和旧证据新尺复评策略明确记录；不原地重写历史报告或已发布 tag。

验收：静态契约与负向自测、旧 schema 样本保留、字段迁移可追溯、SR-17、23、26、30。不得通过删除断言让失败测试“通过”。

### M6：行为评测与发布判断

测试设计从 M0 起并行准备；实际比较在候选版本冻结后进行。负责：独立执行者 + 领域 reviewer。按 [评测计划](04-evaluation-plan.md) 比较无 skill、0.6.0 与候选版本。

输出：原始运行证据、问题/合理省略匹配、错误归因、成本与限制、推荐支持范围。发布说明区分静态通过、合成演练、真实宿主、真人校准，不能以一项替代另一项。

验收：对关键安全和真实性场景不留已知违规；对查漏和误报改进有实际可检查结果；未覆盖品类和工具如实标明，不宣称已验证“绝大部分游戏”。

## 6. 建议拆分的实施 PR

第一批交前置流程与最小能力契约，带相应静态/合成测试；第二批交交接、回归和报告迁移；第三批按需求交付执行/品类适配和真实评测。每批只能在已批准的接口上推进，避免多个 Agent 同时改分级和证据含义。

版本同步与兼容测试必须随实际契约修改一起提交，不能留到最后一次“整理 PR”才修。M5 是收敛工作，不是允许 M1–M4 先产生互不兼容的正式发行。

## 7. 明确不做

本提案不要求所有游戏都有存档、教程、战斗、成长、多人或特定相机；不把缺功能全部判 P0；不以成熟商业规模衡量个人 MVP；不取消后续深度试玩、真人方案或可选评论评分；不默认全面代码、安全或商业发布认证；不自动修改、安装或部署被评游戏；不虚构独立 Agent、长时间试玩或验证结果。
